Android Boot Flow and Partition Layout for Custom SBCs

Trace Android SBC boot from SoC ROM and AVB to first-stage init, then review boot images, dynamic partitions, slots, and factory recovery.
2026-11-07 · 4 min · Embedded SBC Team

An Android board that resets before the kernel and a board that hangs on its boot animation can look identical to an operator. At the bench they are different failure domains. The first may never have selected or verified an image. The second has usually passed through much of the boot chain and needs evidence from userspace. Define what you can observe at each handoff before production disables developer interfaces.

Use the embedded firmware BSP documentation to keep a product-specific boot map next to the flashing manifest. Update it when the board, bootloader, launch Android version, image format or slot scheme changes.

Trace the handoff from ROM to Android#

The SoC’s boot ROM follows the vendor’s boot-media and trust rules. Early firmware initializes enough of the device to load subsequent stages and ordinarily brings up DRAM. The bootloader chooses the boot target or slot, carries out the configured verification policy, and supplies the kernel with the appropriate command line, device tree and ramdisk components. The exact stage names and images vary by SoC and BSP. AOSP bootloader overview.

Android Verified Boot (AVB) establishes trust in Android images according to the device’s key and verification configuration. A vbmeta image can contain verification descriptors or references to chained metadata. Rollback protection also relies on a correctly implemented trusted storage and update policy. A booting engineering image is weak evidence for the locked production boot chain. Validate the secure boot key policy and signing handoffs with the production configuration. Android Verified Boot documentation.

AOSP places the generic ramdisk in the generic boot image for the Android 12 layout described in its guide and uses separate init_boot for devices launching with Android 13 under the documented design. Upgrading an earlier device can retain its previous arrangement. Check the board build configuration and the vendor’s supported path before copying a partition table from another product. Generic boot partition · Vendor boot partitions.

After entry into the kernel, first-stage init needs the storage and filesystem stack to find and mount early partitions, including the logical devices when dynamic partitions apply. A successful kernel print can precede a failure to locate the intended volume. Preserve the build’s generated partition metadata, fstab and boot parameters together. AOSP dynamic partition implementation.

Size the layout using the generated images from both the baseline and a plausible larger release. Check group limits, space required by the selected update mechanism, recovery tooling and the minimum free user data your product needs. Keep separate figures for physical partitions, logical partition groups and temporary update requirements. Factory flashing and an in-field upgrade exercise different paths, so retain evidence for both.

Use the first missing event to narrow the problem#

Last confirmed eventNext evidence to collect
Power and reset onlyBoot-media selection, boot ROM recovery behavior and early supply sequencing
Slot selectedLocked boot state, expected key chain, correct slot image bundle and rollback state
Kernel startsCorrect DTB, vendor ramdisk modules and root storage availability
First-stage init runsFstab, logical partition names, mapping and verified mount results
Android services startRequired HAL registrations, SELinux audit logs and application readiness

Start with a signed image set recorded in the release manifest. Compare the selected slot and expected build fingerprints before changing any component. One replacement image from a different build can produce a downstream failure and obscure the original defect. Apply a device tree review when storage or peripheral probes differ across variants.

Release with observable recovery#

Document which actions are permitted in the locked factory, service and field roles. Establish how the system reports an unsuccessful slot and confirm rollback to the known-good image under the approved policy. On a representative test unit, trigger an interrupted update at agreed boundaries and have the service team use the documented recovery path. Verify encrypted data and persistent identity where applicable. The Android OTA rollback and Android compatibility testing plans should refer to the same production build.

Retain the partition map, expected boot milestones, build manifest, signing configuration references and recovery outcomes as release evidence. It should be possible to identify the failed handoff without guessing from the animation on the front panel.
